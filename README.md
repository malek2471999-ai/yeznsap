# Yeznsap E2EE Messenger — v4.5

Yeznsap v4.5 هو تطبيق مراسلة مباشرة يعتمد على **Username + مفتاح استرداد من 16 كلمة** بدون رقم هاتف أو بريد كشرط للتسجيل. في هذا الإصدار أضيف تشفير طرف إلى طرف فعلي للمحادثات النصية المباشرة، مع بقاء الخادم مسؤولًا عن الحسابات والجلسات وتمرير الـCiphertext فقط.

## ما تغير في v4.5؟

- مفتاح الاسترداد المكوّن من 16 كلمة يُنشأ **داخل المتصفح باستخدام Web Crypto** ولا يُرسل إلى الخادم.
- المتصفح يشتق `authSecret` منفصلًا من مفتاح الاسترداد، والخادم يخزن له `scrypt + salt + pepper` فقط.
- كل حساب ينشئ محليًا زوجي مفاتيح: **RSA-OAEP 3072-bit / SHA-256** لتغليف مفاتيح المحادثات و**ECDSA P-256 / SHA-256** لتوقيع اتفاق مفتاح المحادثة.
- مفاتيح الهوية الخاصة لا تُرفع كنص واضح؛ تُجمع داخل Bundle محلي ثم تُشفّر بـ **AES-256-GCM** باستخدام مفتاح مشتق من كلمات الاسترداد عبر **PBKDF2-SHA256 / 600,000 iterations**.
- عند إنشاء محادثة مباشرة يتم إنشاء مفتاح محادثة عشوائي 256-bit.
- مفتاح المحادثة يُغلّف منفصلًا لكل طرف باستخدام مفتاحه العام RSA-OAEP.
- منشئ المحادثة يوقّع **اتفاق مفتاح المحادثة** بـ ECDSA، ويشمل `keyId` والمشاركين وSHA-256 لمفتاح AES؛ الطرف الآخر يتحقق من التوقيع قبل قبول المفتاح. هذا يمنع الخادم من استبدال مفتاح محادثة قائم بصمت بعد إنشائه الصحيح.
- نص كل رسالة يُشفّر في المتصفح بـ **AES-256-GCM** مع IV عشوائي 96-bit وAAD مرتبط بالمحادثة/الرسالة/المرسل.
- Endpoint الإرسال لا يقبل `text` أصلًا؛ يقبل فقط `iv + ciphertext + message id`.
- الخادم يعيد Ciphertext للطرف الآخر، وفك التشفير يتم داخل المتصفح.
- تظهر بصمة SHA-256 لمفتاح الطرف الآخر داخل رأس المحادثة، ويتم تثبيتها محليًا بأسلوب TOFU؛ تغير المفتاح يوقف فتح المحادثة حتى تتم مراجعته.
- مخزن الخادم نفسه ما زال مشفرًا أيضًا بـ AES-256-GCM كطبقة At-Rest مستقلة.

## مهم: هذا ليس Signal Protocol

هذه النسخة فيها **E2EE حقيقي للمحادثات النصية المباشرة**، لكنها لا تستخدم Signal Protocol أو Double Ratchet. لذلك لا تدّعي الميزات التالية بعد:

- Perfect Forward Secrecy على مستوى Ratchet.
- Post-compromise security.
- X3DH / PQXDH.
- Sender Keys للمجموعات.
- تشفير الوسائط والمكالمات الجماعية بنظام Signal.

إذا انكشف مفتاح المحادثة طويل الأجل الخاص بمحادثة معينة، فقد تصبح رسائل تلك المحادثة المحفوظة قابلة للفك. هذه نقطة مختلفة عن Double Ratchet ويجب عدم إخفائها.

## ماذا يرى الخادم؟

للرسائل الجديدة في v4.5 لا يرى الخادم نص الرسالة أو مفتاح المحادثة الخام أو كلمات الاسترداد. لكنه ما زال يرى Metadata لازمة للخدمة مثل:

- أسماء المشاركين في المحادثة.
- أوقات الرسائل.
- أحجام الـCiphertext تقريبًا.
- حالة الجلسات وعناوين IP بشكل Hash داخل الـAudit Log.

كما أن الخادم يوزع المفاتيح العامة؛ لذلك **تحقق من البصمة مع الطرف الآخر خارج Yeznsap** للمحادثات الحساسة، خصوصًا عند أول اتصال.

## الحسابات القديمة

v4.5 غيّر نموذج المصادقة بحيث لا تصل كلمات الاسترداد إلى الخادم. لهذا السبب الحسابات المنشأة بنسخ v4.4 وما قبلها لا تُسجل الدخول تلقائيًا في وضع v4.5 الآمن. للاختبار الأنظف أنشئ حسابات جديدة في v4.5.

## ميزات الأمان الأخرى الموجودة

- 16 كلمة من قائمة 256 كلمة = 128-bit من entropy لاختيار المفتاح.
- scrypt + salt + pepper للمصادقة على الخادم.
- TOTP + Backup Codes.
- PIN لقفل الجلسة الحالية.
- HttpOnly / Secure production / SameSite=Strict cookies.
- Device-bound server sessions.
- CSRF token + Origin/Fetch-Metadata checks.
- Rate limiting وKDF concurrency limits.
- تشفير `data/store.enc` بـ AES-256-GCM.
- Data export مشفر وحذف نهائي للحساب.
- CSP / HSTS في الإنتاج / no-store للـAPI.
- Security source audit + Node syntax checks + GitHub CI.

## التشغيل

يتطلب Node.js 20 أو أحدث.

```bash
npm install
npm run setup
npm start
```

ثم افتح:

```text
http://localhost:3000
```

على Windows يمكنك تشغيل:

```text
START-YEZNSAP-WINDOWS.bat
```

لا تفتح `public/index.html` عبر `file://` لأن المصادقة والجلسات والرسائل تحتاج Backend.

## الإنتاج

قبل استخدام حقيقي:

1. استخدم HTTPS فقط ودومين ثابتًا.
2. ضع `DATA_ENCRYPTION_KEY`, `DATA_INDEX_KEY`, و`AUTH_PEPPER` في Secret Manager منفصل.
3. انقل التخزين من ملف واحد إلى قاعدة بيانات مناسبة؛ مخزن الملف الحالي جيد للتطوير وليس للتوسع الكبير.
4. نفذ اختبار اختراق ومراجعة Cryptography مستقلة.
5. راجع Fingerprint UX وKey-change recovery قبل إطلاق واسع.
6. إذا كان هدفك Signal/Double Ratchet فعلًا، استخدم تنفيذًا مدققًا ولا تستبدله ببروتوكول مخصص يدّعي أنه Signal.

## الفحص

```bash
npm run check
npm test
npm audit --omit=dev --audit-level=high
```

يوجد اختبار Web Crypto مستقل داخل `tests/e2ee-webcrypto.test.js` يتحقق من هويتي RSA+ECDSA، اتفاق مفتاح موقّع، تغليف مفتاح محادثة لطرفين، تبادل AES-GCM، رفض العبث بالـAAD، ورفض اتفاق مفتاح تم تعديله.

راجع كذلك `SECURITY.md`, `THREAT_MODEL.md`, و`PRODUCTION_CHECKLIST.md`.
